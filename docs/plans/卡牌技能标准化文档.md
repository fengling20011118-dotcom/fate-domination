# 卡牌技能标准化文档

状态：阶段性确认稿  
日期：2026-09-02  
范围：御主、从者、技能牌、事件牌、局势牌的人工维护型结构化数据设计。  

本文记录已经确认的结构化设计原则。未确认的能力类型、枚举全集和具体卡牌映射不在本文强行补全。

## 1. 总体方向

使用“人工维护格式 + 编译展开格式 + 主仓库运行时适配”的路线。

```text
人工维护 JSON
  -> 编译器展开默认值
  -> canonical/runtime JSON
  -> 适配主仓库 LegacyContentPackage / StandardContent / SkillDefinition / CardDefinition
```

人工维护 JSON 允许短写。canonical/runtime JSON 由编译器补齐默认值后供校验、测试和主仓库适配使用。

## 2. ID 原则

正式结构化数据使用主仓库 canonical ID 作为主键。

示例：

```text
servant.drake
servant.suzuka
master.kiritsugu
master.shinji
master.kayneth
master.maiya
master.dan
master.julius
```

本地旧 ID 只允许作为 `aliases` 保留，不再作为运行时、测试、UI 或导出的主键。

示例：

```json
{
  "id": "servant.drake",
  "aliases": ["servant.francis_drake"]
}
```

## 3. 卡牌与能力拆分

所有技能卡、事件牌、局势牌的规则能力统一放入 `abilities[]`。

即使一张卡只有一个能力，也使用 `abilities[]`，避免简单卡和复杂卡出现两套表达方式。

每个 `ability` 必须保留对应原文片段：

```json
{
  "id": "mount_summon",
  "printedClause": "坐骑召唤-行动阶段：打出至多3张基本威力为3或更低的手牌。"
}
```

每张卡必须保留完整原文：

```json
{
  "printedText": "打出时：若此牌与一张基础攻击一同打出，抽一张牌。\n坐骑召唤-行动阶段：打出至多3张基本威力为3或更低的手牌。"
}
```

任何无法映射进 `abilities[]` 的原文必须进入 `unmodeledClauses` 或 `ambiguities`。

## 4. 卡牌本体字段分层

卡牌本身的费用、威力、属性、发动门槛不放进 `activation`。

字段边界：

| 信息 | 字段 |
|---|---|
| 卡牌牌面费用 | `cardFace.cost` |
| 卡牌牌面威力 | `cardFace.basePower` |
| 卡牌属性 | `cardFace.attributes` |
| 卡牌牌面门槛 | `cardFace.requirements` |
| 可执行打出条件 | `playRequirements` |
| 能力发动时点 | `ability.activation` |
| 能力额外费用 | `ability.cost` |
| 能力发动/结算条件 | `ability.conditions` |
| 玩家/房主需要选择的目标 | `ability.targets` |
| 能力效果 | `ability.effects` |

`activation` 只表达时点，不承载费用、威力、目标或效果。

## 5. 响应窗口

响应能力仍放在 `abilities[]` 中，不单独开 `responses[]`。

```json
{
  "kind": "response"
}
```

已确认规则：

1. 响应多人顺序默认 `turn_order`。
2. 非资格玩家只看到“等待响应结算”，不显示响应者身份和响应来源。
3. pass 默认语义为 `decline_this_window`。
4. `responseWindow.opens` 对 `kind: "response"` 必须显式填写，不能从中文文本自动推断。
5. authoring JSON 允许短写，canonical/runtime JSON 由编译器展开默认值。

人工维护短写示例：

```json
{
  "id": "post_power_response",
  "printedClause": "战力结算后：你可以弃置此牌，获得3战果。",
  "kind": "response",
  "activation": {
    "phase": "combat",
    "step": "post_power_calculation"
  },
  "responseWindow": {
    "opens": "after_combat_power_calculated"
  },
  "cost": {
    "type": "discard_self"
  },
  "effects": [
    {
      "type": "gain_victory_points",
      "target": "controller",
      "amount": 3
    }
  ]
}
```

编译展开后的默认结构：

```json
{
  "responseWindow": {
    "opens": "after_combat_power_calculated",
    "responders": {
      "type": "controller"
    },
    "priority": "turn_order",
    "visibility": {
      "windowVisibleTo": "eligible_players",
      "waitingVisibleTo": "all_players",
      "waitingLabelForNonEligible": "等待响应结算",
      "hideEligibleResponderIdentity": true,
      "sourceVisibleBeforeResolve": "controller_only",
      "sourceVisibleAfterResolve": "public_if_revealed",
      "revealSourceOnResolve": true
    },
    "closeCondition": "controller_resolves_or_passes",
    "passBehavior": "decline_this_window"
  }
}
```

多人响应时覆盖：

```json
{
  "responseWindow": {
    "closeCondition": "all_eligible_players_pass_or_resolve"
  }
}
```

抢占式响应时覆盖：

```json
{
  "responseWindow": {
    "closeCondition": "first_response_resolves"
  }
}
```

房主裁定响应时覆盖：

```json
{
  "responseWindow": {
    "closeCondition": "host_closes"
  }
}
```

## 6. 目标选择

`targets[]` 只写玩家或房主需要实际选择的目标。

自动解析目标直接写在 `effect.target` 中。

示例：

```json
{
  "effects": [
    {
      "type": "defeat_players",
      "target": {
        "type": "highest_power_engaged_opponents"
      }
    }
  ]
}
```

需要玩家选择时使用 `targets[]`：

```json
{
  "targets": [
    {
      "id": "targetOpponent",
      "type": "player",
      "scope": "engaged_opponents"
    }
  ],
  "effects": [
    {
      "type": "defeat_player",
      "target": "targetOpponent"
    }
  ]
}
```

已确认规则：

1. `targets[]` 只写玩家/房主需要实际选择的目标。
2. 自动解析目标直接写在 `effect.target`。
3. `targets[].visibility` 默认 `public`。
4. 涉及手牌、牌库、暗置牌、秘密记录时，必须显式声明私密策略。
5. `conditions` 表示能力是否能发动/结算。
6. `target.constraints` 表示候选目标是否合法。
7. `count` 默认 `{ "min": 1, "max": 1 }`。
8. `count.min = 0` 时，`required` 默认 `false`。
9. `count.min >= 1` 时，`required` 默认 `true`。
10. authoring JSON 允许短写，canonical JSON 由编译器展开。

目标可见性枚举第一版：

```text
public
private_to_controller
private_to_host
reveal_result_only
hidden_until_resolved
```

目标条件边界：

```text
conditions = 能力是否能发动/结算
target.constraints = 某个候选目标是否合法
```

## 7. 主持人裁定

主持人裁定只解决一个问题：

```text
能力当前不能自动执行时，系统如何安全暂停，并限制房主只能执行少量允许操作。
```

裁定信息只放在 `ability.execution`。

已确认规则：

1. 裁定信息只放在 `ability.execution`。
2. `host_adjudicated` 默认只在测试/开发房开放，正式房禁用。
3. `allowedOperations` 第一版严格使用主仓库已有 5 种。
4. 人工维护时可以短写，编译器补默认值。
5. `text_unconfirmed` 和 `unsupported` 不生成玩家可用操作，只进入待确认/待实现清单。

允许操作第一版：

```text
adjust-mana
adjust-victory-points
move-card
create-status
skip-ability
```

人工维护短写：

```json
{
  "execution": {
    "mode": "host_adjudicated",
    "reason": "effect_not_modeled"
  }
}
```

编译展开：

```json
{
  "execution": {
    "mode": "host_adjudicated",
    "reason": "effect_not_modeled",
    "allowedOperations": [
      "adjust-mana",
      "adjust-victory-points",
      "move-card",
      "create-status",
      "skip-ability"
    ]
  }
}
```

`text_unconfirmed` 和 `unsupported` 示例：

```json
{
  "execution": {
    "mode": "text_unconfirmed",
    "reason": "ocr_uncertain"
  }
}
```

```json
{
  "execution": {
    "mode": "unsupported",
    "reason": "runtime_gap"
  }
}
```

## 8. 隐藏信息与真名解放

隐藏信息采用“区域默认 + 卡牌覆盖”的设计。

已确认规则：

1. 手牌、牌库、暗置攻击、新都暗置事件等主要由 zone 默认可见性控制。
2. 卡牌 schema 只在突破默认规则时写 `visibility` 或 `visibilityOverrides`。
3. 带【真名解放】标记的 ability 被使用时，默认在声明使用时公开。
4. 公开范围是 `servant_package`。
5. 公开后，该从者后续不再按隐藏真名处理。

带【真名解放】的能力短写：

```json
{
  "id": "noble_phantasm",
  "printedClause": "【真名解放】战斗阶段：……",
  "markers": ["真名解放"],
  "kind": "phase_action",
  "activation": {
    "phase": "combat"
  }
}
```

编译器展开：

```json
{
  "visibility": {
    "revealsTrueName": true,
    "revealTiming": "on_use_declared",
    "revealScope": "servant_package"
  }
}
```

`servant_package` 第一版包括：

```text
从者身份
从者职阶
从者公开资料
从者技能牌
已知从者专属卡牌定义
```

## 9. 残留、持续与清理生命周期

残留、持续和清理生命周期统一使用 `ability.lifecycle` 表达。

已确认规则：

1. `effects` 只负责创建一次性效果、持续效果或 modifier。
2. `lifecycle` 负责持续时间、开始时点和清理方式。
3. 【残留】效果默认在打出的当回合立即生效，除非卡牌文字明确指定其他开始时点。
4. `lifecycle` 命名空间下可使用 `duration`、`starts`、`cleanup`、`expiresOn`，避免和主仓库或本地已有顶层字段冲突。

基础结构：

```json
{
  "lifecycle": {
    "duration": "while_active",
    "starts": "immediate",
    "cleanup": "remain_active",
    "expiresOn": ["card_closed"]
  }
}
```

`duration` 第一版建议值：

```text
this_round
while_active
until_card_closed
until_condition_met
permanent
```

`starts` 第一版建议值：

```text
immediate
next_round
next_phase
on_condition_met
```

`cleanup` 第一版建议值：

```text
close_at_round_end
remain_active
discard_at_round_end
return_to_deck_on_defeat
remove_from_game
```

普通本回合持续效果：

```json
{
  "effects": [
    {
      "type": "create_modifier",
      "modifier": {
        "type": "power_bonus",
        "target": "controller_basic_attacks",
        "amount": 2
      }
    }
  ],
  "lifecycle": {
    "duration": "this_round",
    "starts": "immediate"
  }
}
```

【残留】效果短写：

```json
{
  "kind": "residual",
  "printedClause": "残留：回合结束时，获得1点魔力。",
  "lifecycle": {
    "duration": "while_active"
  },
  "effects": [
    {
      "type": "gain_mana",
      "target": "controller",
      "amount": 1
    }
  ]
}
```

编译器展开：

```json
{
  "kind": "residual",
  "lifecycle": {
    "duration": "while_active",
    "starts": "immediate",
    "cleanup": "remain_active"
  }
}
```

主仓库适配时，`kind: "residual"` 应继续映射到主仓库已有的 `activation.kind = "residual"` 或 `residual: true` 语义，但不得丢失 `starts: "immediate"`。

## 10. 改写基础规则的能力

改写基础规则的能力统一使用 `ability.ruleModifiers[]` 表达。

这类能力不是一次性结算结果，而是改变规则入口、合法性检查、费用计算、移动规则、出牌规则、战力修正、奖励限制或令咒选项。

示例：

```text
你的【急行】可以反向移动。
你的基础攻击威力+2。
本回合你无法获得战果。
你无视局势牌限制。
你的令咒效果改为……
```

已确认规则：

1. 改写基础规则的能力统一用 `ruleModifiers[]`，不塞进普通 `effects`。
2. `ruleModifiers[]` 放在 ability 下。
3. 每个 `ruleModifier` 必须保留 `printedClause`；如果和 ability 共用同一句，可以继承 `ability.printedClause`。
4. `operation` 第一版只允许：`allow`、`forbid`、`replace`、`add`、`subtract`、`set`、`ignore`。
5. `ruleModifier.lifecycle` 可省略并继承 `ability.lifecycle`。
6. 如果 ability 和 ruleModifier 都没有 lifecycle，则该 modifier 必须是明确永久或由专属 handler 管理，否则进入 `host_adjudicated`。

基础结构：

```json
{
  "ruleModifiers": [
    {
      "id": "dash_reverse_movement",
      "printedClause": "被动：你的【急行】可以反向移动。",
      "type": "movement_rule_override",
      "scope": {
        "subject": "controller",
        "object": "card_named",
        "cardName": "急行"
      },
      "operation": "allow",
      "rule": "reverse_movement"
    }
  ]
}
```

基础攻击威力修正：

```json
{
  "ruleModifiers": [
    {
      "id": "basic_attack_power_plus_2",
      "printedClause": "你的基础攻击威力+2。",
      "type": "combat_power_modifier",
      "scope": {
        "subject": "controller",
        "object": "basic_attacks"
      },
      "operation": "add",
      "rule": "card_base_power",
      "value": 2,
      "lifecycle": {
        "duration": "this_round"
      }
    }
  ]
}
```

禁止获得战果：

```json
{
  "ruleModifiers": [
    {
      "id": "forbid_gain_vp",
      "printedClause": "本回合你无法获得战果。",
      "type": "reward_rule_override",
      "scope": {
        "subject": "controller"
      },
      "operation": "forbid",
      "rule": "gain_victory_points",
      "lifecycle": {
        "duration": "this_round"
      }
    }
  ]
}
```

若 `ruleModifier.lifecycle` 省略，则继承 `ability.lifecycle`：

```json
{
  "lifecycle": {
    "duration": "while_active"
  },
  "ruleModifiers": [
    {
      "id": "basic_power_bonus",
      "operation": "add",
      "rule": "card_base_power",
      "value": 2
    }
  ]
}
```

## 11. 生成、复制与派生卡牌

生成、复制、派生卡牌类能力先采用主模板，不在第一版中强求覆盖所有复杂细节。

涉及此类复杂机制的卡牌，通常需要人工多次确认。若来源、目标、继承范围、生命周期或公开状态存在不确定，应进入 `ambiguities` 或 `host_adjudicated`，不得凭 OCR 或自然语言猜测。

已确认规则：

1. 生成、复制、派生卡牌不全部塞进普通 `effects`。
2. 创建新对象用 `creates[]`。
3. 复制已有对象的属性、威力、费用或能力用 `copies[]`。
4. 改变已有对象的定义、形态、区域或明暗状态用 `transforms[]`。
5. `creates[]`、`copies[]`、`transforms[]` 放在 ability 下。
6. 它们可以有自己的 `lifecycle`；没有时继承 `ability.lifecycle`。
7. 如果既没有自身 lifecycle，也没有 ability lifecycle，则必须是明确永久一次性变更，否则进入 `host_adjudicated`。

分类边界：

```text
creates[]     创建新对象
copies[]      复制已有对象的部分规则、数值、属性或能力
transforms[]  改变已有对象的定义、形态、区域或明暗状态
```

创建新卡牌：

```json
{
  "creates": [
    {
      "id": "create_origin_bullet",
      "printedClause": "将2张游戏外的起源弹加入手牌。",
      "type": "card",
      "definitionId": "card.derived.master.kiritsugu.origin_bullet",
      "count": 2,
      "destination": {
        "zone": "hand",
        "owner": "controller"
      },
      "source": "outside_game",
      "lifecycle": {
        "duration": "permanent"
      },
      "visibility": "private_to_controller"
    }
  ]
}
```

创建临时攻击：

```json
{
  "creates": [
    {
      "id": "create_temporary_attack",
      "type": "card",
      "definition": {
        "cardType": "servant_attack",
        "name": "临时攻击",
        "attributes": ["力量"],
        "basePower": 2,
        "cost": 0
      },
      "count": 1,
      "destination": {
        "zone": "attack",
        "owner": "controller"
      },
      "source": "effect",
      "lifecycle": {
        "duration": "this_round",
        "cleanup": "remove_from_game"
      },
      "visibility": "public"
    }
  ]
}
```

复制属性、威力、费用或能力：

```json
{
  "copies": [
    {
      "id": "copy_top_card_stats",
      "printedClause": "获得此牌上的牌堆顶部牌的威力、费用、属性与能力。",
      "from": {
        "type": "card",
        "scope": "attached_stack_top"
      },
      "to": {
        "type": "card",
        "scope": "this_card"
      },
      "aspects": [
        "basePower",
        "cost",
        "attributes",
        "abilities"
      ],
      "lifecycle": {
        "duration": "while_active"
      }
    }
  ]
}
```

改变已有对象：

```json
{
  "transforms": [
    {
      "id": "become_attack",
      "printedClause": "若其不是一张攻击，变成攻击。",
      "target": "targetCard",
      "changes": {
        "cardType": "servant_attack"
      },
      "lifecycle": {
        "duration": "while_active"
      }
    }
  ]
}
```

如果 `creates[]`、`copies[]` 或 `transforms[]` 的生命周期省略，则继承 `ability.lifecycle`：

```json
{
  "lifecycle": {
    "duration": "this_round"
  },
  "copies": [
    {
      "id": "copy_attributes",
      "aspects": ["attributes"]
    }
  ]
}
```

## 12. 数值公式能力

数值公式能力用于表达依赖当前状态、目标、历史记录或前序效果结果的动态数值。

典型例子：

```text
X 为本回合移动距离的 4 倍。
失去三分之一魔力，向上取整。
获得等同于其失去魔力值二倍的威力。
每经过或停留一个战场获得 1 战果。
威力等于某张牌当前威力。
按事件牌 VP 总和计算。
```

已确认规则：

1. 数值字段允许固定值或 `formula`。
2. authoring JSON 可以短写公式。
3. canonical/runtime JSON 必须展开为受控公式 AST。
4. 不允许 runtime 执行任意字符串公式。
5. 公式无法稳定展开时，进入 `host_adjudicated` 或 `text_unconfirmed`。
6. 公式必须能生成 calculation lines，方便 UI 展示费用、战力、奖励和触发明细。

固定值：

```json
{
  "type": "gain_mana",
  "amount": 2
}
```

人工维护短写公式：

```json
{
  "type": "gain_power",
  "amount": {
    "formula": "movement_distance_this_round * 4"
  }
}
```

canonical/runtime 展开为受控公式 AST：

```json
{
  "type": "gain_power",
  "amount": {
    "type": "formula",
    "op": "multiply",
    "args": [
      {
        "type": "metric",
        "metric": "movement_distance_this_round",
        "source": "controller"
      },
      {
        "type": "constant",
        "value": 4
      }
    ]
  }
}
```

向上取整示例：

```json
{
  "amount": {
    "type": "formula",
    "op": "ceil",
    "args": [
      {
        "type": "formula",
        "op": "divide",
        "args": [
          {
            "type": "metric",
```

## 13. 限制、无视、禁止类效果

限制、无视、禁止类效果统一使用 `ability.ruleModifiers[]` 表达。

这类能力会改变规则入口、合法性判断或冲突裁定，不应作为普通一次性 `effects` 处理。

典型例子：

```text
你无法获得战果。
你无视【败北】效果。
禁止使用宝具。
不能移动。
此牌威力不能被减少。
无视局势牌限制。
该地点无法使用特殊攻击。
你不受某效果影响。
```

已确认规则：

1. 限制、无视、禁止类能力统一使用 `ruleModifiers[]`。
2. 不单独开顶层 `restrictions[]` 或 `immunities[]` 作为主结构。
3. `operation` 继续使用已确认枚举：`allow`、`forbid`、`replace`、`add`、`subtract`、`set`、`ignore`。
4. `ruleModifier` 可选 `priority`，默认按来源推导。
5. `priority` 第一版包括 `tier` 和 `specificity`。
6. 默认冲突策略：明确例外 > 具体对象 > forbid > allow；仍无法判断时进入 `host_adjudicated`。
7. 如果卡牌文字本身就是“无视/不能/禁止/无法”，必须保留 `printedClause`，不能只写结构化结果。

`priority.tier` 第一版：

```text
base_rule
situation
event
card_text
mode_rule
host_ruling
```

`priority.specificity` 第一版：

```text
general
normal
specific
explicit_exception
```

`conflictPolicy` 第一版：

```text
forbid_over_allow
explicit_exception_over_general
latest_effect_wins
higher_priority_wins
host_required
```

默认冲突顺序：

```text
1. 明确例外优先于一般禁止/允许。
2. 具体对象优先于泛对象。
3. 同一具体度下，forbid 优先于 allow。
4. 同一来源、同一具体度且互相矛盾时，进入 host_adjudicated。
```

禁止获得战果：

## 14. 主仓库格式适配器

本格式必须通过 adapter 接入主仓库开发主线。

adapter 的目标不是把人工维护格式压扁成主仓库旧格式，而是：

```text
向主仓库旧字段提供最低兼容；
向 rules 扩展保留完整语义；
向 report 暴露未联通风险。
```

## 14.1 适配目标

第一阶段 adapter 目标：

1. 主仓库现有字段可继续 `validate`、加载并进入 `buildStandardContent()`。
2. 我们确认过的完整结构化语义保留在 `rules` 扩展字段中。
3. 无法自动映射、需要专属 handler、需要主持人裁定或需要人工确认的内容进入 adapter report。

adapter 输出不要求第一阶段让所有能力完全自动执行，但不得丢失已确认语义。

## 14.2 输入与输出

输入为人工维护格式：

```json
{
  "id": "servant.drake.skill.sc-drake-1",
  "aliases": ["servant.francis_drake.skill.riding"],
  "name": "骑乘（Rider Class）",
  "printedText": "打出时：若此牌与一张基础攻击一同打出，抽一张牌。\n坐骑召唤-行动阶段：打出至多3张基本威力为3或更低的手牌。",
  "cardFace": {
    "typeLabel": "特殊",
    "cost": 3,
    "requirement": {
      "type": "min_mana",
      "value": 3
    },
    "basePower": 0,
    "attributes": ["特殊"]
  },
  "abilities": [],
  "evidence": [],
  "verification": {}
}
```

输出到主仓库兼容格式：

```json
{
  "id": "servant.drake.skill.sc-drake-1",
  "name": "骑乘（Rider Class）",
  "typeLabel": "特殊",
  "cost": 3,
  "requirement": 3,
  "basePower": 0,
  "text": "打出时：若此牌与一张基础攻击一同打出，抽一张牌。\n坐骑召唤-行动阶段：打出至多3张基本威力为3或更低的手牌。",
```

## 14.3 字段映射

| authoring 字段 | 主仓库字段 |
|---|---|
| `id` | `id` |
| `aliases` | `rules.aliases`，必要时补充到 `legacyId` |
| `name` | `name` |
| `printedText` | `text` |
| `cardFace.typeLabel` | `typeLabel` |
| `cardFace.cost` | `cost` |
| `cardFace.basePower` | `basePower` |
| `cardFace.requirement` | `requirement` / `requiresEightMana` |
| `cardFace.attributes` | `attributes` |
| `abilities[].activation.phase` | `activation.windows` 汇总 |
| `abilities[].activation.step` | `activation.steps` 汇总 |
| `abilities[].kind` | `activation.kind` 推导 |
| `abilities[].execution.mode` | `implementation` / `supportLevel` |
| `evidence` | `sourceRefs` |
| 完整人工维护结构 | `rules` 扩展字段 |

## 14.4 多 ability 汇总规则

主仓库当前多数技能只有一个 `activation`，而人工维护格式允许一张卡拥有多个 `abilities[]`。

adapter 应按以下规则汇总：

```text
activation.windows = 所有 ability.activation.phase 去重集合
activation.steps = 所有 ability.activation.step 去重集合
activation.kind = 按最高复杂度能力推导
```

`kind` 推导优先级第一版：

```text
residual > response > phase_action > play_trigger > passive
```

主仓库兼容映射：

```text
residual -> residual
response -> reaction；若主仓库运行时不支持 reaction，则降级为 phase 并在 report 中记录
phase_action -> active / phase
play_trigger -> play
passive -> passive
```

## 14.5 implementation 映射

第一版映射规则：

```text
所有 ability.execution.mode 都是 automatic
  -> implementation = implemented 或 supportLevel = FULL

存在 host_adjudicated
  -> implementation = pending 或 supportLevel = MANUAL/PARTIAL

存在 text_unconfirmed
  -> implementation = pending，并在 adapter report 中标为 error

存在 unsupported
  -> implementation = disabled，或不导入正式包
```

adapter 不得把 `text_unconfirmed`、`unsupported` 或无法映射的能力静默标记为完整实现。

## 14.6 rules 扩展保留

adapter 必须在主仓库兼容对象中保留完整 `rules` 扩展：

```json
{
  "rules": {
    "schemaVersion": "fd-card-authoring-v1",
    "aliases": [],
    "cardFace": {},
    "playRequirements": [],
    "abilities": [],
    "evidence": [],
    "verification": {},
    "ambiguities": []
  }
}
```

主仓库旧逻辑可以暂时忽略 `rules`，但后续运行时、校验器和测试可以逐步消费它。

## 14.7 adapter report

不确定内容不能静默降级。

以下情况必须进入 adapter report：

- 未确认文字。
- 无法映射时点。
- 无法映射目标。
- 无法映射公式。
- 无法映射生命周期。
- 无法映射 `ruleModifiers`。
- 与主仓库 canonical ID 对不上。
- 需要专属 handler。
- 需要 `host_adjudicated`。
- 当前排除范围内容被误导入。

报告项格式第一版：

```json
{
  "severity": "error",
  "cardId": "servant.drake.skill.sc-drake-1",
  "field": "abilities[1].targets",
  "message": "Target scope cannot be mapped to main repo AvailableAction input",
  "requiredAction": "add_handler_or_confirm_target_scope"
}
```

`severity` 第一版：

```text
info
warning
error
blocking
```

## 14.8 第一阶段验收标准

第一阶段 adapter 验收标准：

1. 使用主仓库 canonical ID。
2. 能导出 `masters`、`servants`、`cards`、`eventGroups`、`situations`。
3. 主仓库 `npm run validate` 能通过。
4. 主仓库 `buildStandardContent()` 能读取导出结果。
5. 每张精修卡的 `rules` 扩展完整保留。
6. adapter report 明确列出未自动映射项。
7. 不导入当前排除范围内容。

当前排除范围：

```text
巴贝奇
月之癌相关角色
月杯事件组
```

## 14.9 推荐输出文件

adapter 第一阶段推荐输出三个文件：

```text
dist/main-repo/legacy-content.patch.json
dist/main-repo/fd-card-authoring-rules.json
dist/main-repo/adapter-report.json
```

含义：

| 文件 | 用途 |
|---|---|
| `legacy-content.patch.json` | 可合入主仓库 `legacy-content.json` 的兼容字段 |
| `fd-card-authoring-rules.json` | 完整人工确认 rules 结构 |
| `adapter-report.json` | 映射问题、未实现能力、需 handler 能力、需人工确认能力 |
