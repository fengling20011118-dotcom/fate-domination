# Fate/Domination 本地化游戏 PRD

版本：0.1 · 日期：2026-09-03 · 状态：基于源码审计的产品提案，新增范围待负责人确认。

本文中的“本地化”指在 Windows 电脑本机运行、中文可读、保留原桌游规则与隐藏信息的数字游戏，不仅是文字翻译，也不预设必须使用 Electron。已确认规则与卡牌规范继续有效；本文不修改规则书。联网属于共用架构下的后续交付。

当前实现证据见 [本地与主仓库实现审计](../reports/2026-09-03-本地与主仓库实现审计.md)。本次仅编写产品与审计文档，不代表下列功能已经实现，也未提交或合并远端 PR。

## 1. 产品主线

**让玩家在本机打开游戏，选择角色，在 3-7 人标准局中完成一场十一回合圣杯战争；费用、时点、响应、战力和胜负由同一个权威规则核心处理，卡牌中文原文和结算依据随时可查，对局可保存并继续。**

建议以 GitHub 主仓库 V2 作为最终集成与发布工程，以本地已经确认的规则、人工维护卡牌档案和解释器样例作为接入来源。主仓库是代码集成主线，不自动成为所有规则冲突的裁定者。

所有开发任务至少归属一个可验收结果：能开局、能完成合法操作、能正确结算、能保护信息、能恢复对局、能维护内容。单纯增加角色数量、测试数量或页面数量，不等于推进同等比例的产品完成度。

### 1.1 为什么现在需要 PRD

两边并非完全没有方向：主仓库 README 已规定单机与联机共用规则引擎，本地 `apps/client/PRODUCT.md` 已规定电脑端牌桌和后端权威。问题是这些要求没有组成共同的最小发布范围和验收链：

- 本地正式测试入口实际只有五席，旧固定人数界面不能替代 3-7 人配置和每席可执行角色。
- 本地内容包、authoring 解释器和 UI 示例数据并存，尚未由一个应用入口贯通。
- 主仓库有应用契约、技能注册、存档和 AI 骨架，但当前提交缺少被引用模块，干净检出无法通过测试。
- 规则来源存在移动费用等差异；有些已有测试维护的是历史原型规则。
- “内容校验成功”“能力标为 FULL”“画面能展示”“完整对局可玩”缺少分别统计。

### 1.2 路线比较

| 路线 | 收益 | 代价 | 建议 |
|---|---|---|---|
| 主仓库核心 + 本地成果适配，先做 3-7 人标准局闭环 | 最早暴露真实规则和交互断点，成果可直接进入开发主线 | 先解决规则版本与契约适配 | 推荐 |
| 先完成全部角色再接 UI | 大批内容可集中处理 | 海量条款缺少实际交互验证，不能尽早形成游戏 | 作为并行内容工作，不作为首版前置条件 |
| 本地继续独立开发完整游戏，最后整体迁移 | 短期可沿用熟悉代码 | 两套状态、ID、规则和存档持续分化 | 不作为长期产品路线 |

## 2. 用户与核心体验

| 用户 | 核心需求 | 成功表现 |
|---|---|---|
| 熟悉实体游戏的玩家 | 正确复现规则，不手算费用与奖励 | 知道当前该做什么，完成一局后可检查结算依据 |
| 初次使用数字版的玩家 | 中文提示、卡牌检视、明确的非法原因 | 无需控制台、JSON 编辑或开发者口头帮助即可开始并继续游戏 |
| 内容维护者 | 按原始牌面维护结构化档案 | 每个能力能追溯中文原文、证据、实现状态和测试 |
| 测试房主持人 | 对未自动化条款执行受限裁定 | 裁定有来源、有权限、有日志、可恢复，不直接编辑整份状态 |

标准玩家体验：启动 → 新建/继续 → 配置标准局 → 选角与准备 → 十一回合对局 → 淘汰/最终胜负 → 结果与记录。

不把调试视角切换器、内部 handler 名称、OCR 状态和完整权威状态展示给普通玩家。中文牌面与后端计算说明属于玩家信息；实现详情属于开发诊断。

## 3. 版本范围

以下优先级是产品提案，不是对既有代码进度的宣告。

| 版本 | 必须达到的用户结果 | 不作为该版本前置条件 |
|---|---|---|
| P0 / 本地标准局 MVP | 3-7 人标准局可配置；至少支持一名真人与合法代理补足到 3 人；标准十一回合；一套完整事件组；完整局势流程；中文桌面 UI；保存与继续 | 公网房间、账号、全角色自动化、移动端、原生安装器、音效 |
| P1 / 本地多人测试版 | 同一权威核心支持局域网真人加入与掉线恢复；开发房受限裁定完整闭环；扩充已验证角色 | 公网匹配、竞技排名、复杂 AI |
| P2 / 扩展发行 | 3X 完整 UI、更多角色与事件、发行打包、移动端独立布局等按验收逐项加入 | 不以无限扩展拖延 P0 |

P0 代理仅负责合法选择与流程推进，不追求高强度策略；代理用于补足测试人数或单机体验，不是规则强制补到人数上限。代理必须真实部署、出牌、选择目标和参与结算，不能以固定战力或持续空过代替玩家。AI 不调用远程 LLM 决定规则，不读取对手秘密信息或自身未知牌库顺序。

本次沿用用户明确暂缓的巴贝奇、月之癌相关角色。月之癌角色与“月之圣杯事件组”是不同范围，不作同义排除。第一版只启用选定的一套事件组，其他组以后接入。

### 3.1 首版内容清单建议

- 至少三名通过整套能力验收的御主、三名通过整套能力验收的从者；每个实例均有真实牌库、技能和资源。默认不同角色，不通过复制占位角色补足首发名册。
- 本地五名正常从者与独立阿尔托莉雅·卡斯特样例合计提供候选池，不等于已经全部接入。超过三人的首发名册由主仓库现有 canonical 名册选取并确认；不得自行猜测卡面。
- 基础攻击、令咒、角色派生牌必须作为内容依赖一并闭合。一个技能能生成 `card.luck`，不等于幸运牌本身已经实现。
- 首版事件组建议优先评估主仓库已有 `event-group.fuyuki`（冬木，20 槽），可减少事件 ID 与内容入口转换。备选是本地已复核的盈月之仪（20 槽、18 个不同定义）。选其中一组完整实现，不拼成缺牌的混合事件组；最终组名列入发布清单。
- 局势必须覆盖 10 张非高潮候选及 3 张高潮牌，开局非高潮洗混烧毁 2 张，剩余 8 张连接第 9–11 回合固定高潮。主仓库有 13 条局势数据，但逐条自动执行仍需验收。
- 首发正常房仅开放全部必需能力可执行的组合。`PARTIAL`/`HOST_ADJUDICATED` 可以进入明确标识的开发房，不能作为无主持人的正常单机内容。

### 3.2 升华技（已确认澄清）

2026-09-03 用户确认：升华技属于御主，通常是御主卡牌页面的最后一张；从者没有升华技。此前“从者页面末张”的表述已纠正。

内容整理时优先核对御主页面末张牌，保留牌图及 HTM 关联；升华技在御主资料中与本体技能分组展示，不纳入从者三张技能牌。具体费用、使用条件与时点以牌面为准，不能仅凭页面位置推导。正式内容使用主仓库 canonical ID。

当前根客户端的 `master.ascension.demo.tactical_release` 是演示占位：御主归属方向正确，但没有真实升华技内容和执行验收，不能计为已接入。首发内容验收须核对各御主的实际升华技及其适用条件，不用占位补齐。

## 4. 规则基线与决策管理

本地通用规则基线是 [FD-Game-Rules-Final.md](../rules/FD-Game-Rules-Final.md)，卡牌表达以 [卡牌技能标准化文档](../plans/卡牌技能标准化文档.md) 为依据。牌面证据依次采用原始牌图、HTM 关联、已确认通用规则、OCR 草稿。OCR 不直接决定规则或卡牌归属。

用户后续明确修正应保存在带日期和来源的判例记录中；源码与旧整理不得反向修改规则。主仓库规则文本与本地基线冲突时，记录双方证据并由负责人统一 `rulesPackageId` 对应的行为。

本次必须进入统一记录的分歧：

| 议题 | 当前来源差异 | 产品处理 |
|---|---|---|
| 移动费用 | 本地规则 1→2→2；主仓库规则文本与代码 2→2→1 | 本地验收按已确认规则；进入主线前显式统一，禁止 UI 自己选一套 |
| 部署槽位 | 最终规则 §8.2 已按新增基础规则同步为可用位数值由高到低放置 | UI 与后端候选必须按最终规则生成，不再保留旧版空位自选摘要 |
| 标准人数 | 最终规则 1.1.0 支持 3-7 人；少于 3 人时添加 1 名 NPC；本地内容场景五席 | 产品标准房按 3-7 人配置验收，代理只用于补足测试或单机体验 |
| 淘汰与胜负 | 本地原型有军绩阈值淘汰；最终规则按第 8/9/10 回合 VP 截线 | 正式标准局采用最终规则，旧军绩机制不进入产品标准模式 |
| 卡牌规范中的历史排除说明 | 文档额外写过排除月杯事件组，用户后来澄清暂缓对象是月之癌角色 | 发布清单明确当前事件组；若修订旧规范，独立记录，不借本 PRD 静默改写 |

### 4.1 必须保持的规则行为

| 领域 | P0 验收规则 |
|---|---|
| 回合 | 准备→前哨→行动→战斗→战力结算→回合结束→淘汰/胜负→顺位轮转 |
| 开局 | 3-7 人；通常魔力 4、上限 12、令咒 3、手牌补至 3；角色明确例外由后端应用 |
| 常规行动 | 常规移动在常规出牌之前；沿箭头方向从当前地点移动；效果移动有独立语义 |
| 成组出牌 | 通常两张、同批支付；不足时尽可能全部打出；仍有合法牌不能自由空过 |
| 技能牌 | 通常出牌前魔力至少 8；门槛不等于支付费用；阶段能力通常要求来源已经激活 |
| 暗置 | 通常不付魔力、不激活、不计威力；仍计入打出/使用；被动或明确例外按原文处理 |
| 战斗阶段 | 使用此前已激活卡牌的合法战斗能力，不因此获得战斗阶段打牌许可 |
| 响应 | 无通用自由插入栈；仅明确窗口；多人默认 turn_order；pass=decline_this_window |
| 非资格者 | 仅显示“等待响应结算”，不显示私密响应身份、来源和候选 |
| 残留 | 激活后立即适用并按自身生命周期保留，不默认推迟到下回合 |
| 真名 | 使用带相关真名解放条款的能力时按已确认触发公开 servant_package，不因文字提及词条而误触发 |
| 奖励 | 侦查 2 VP；战场事件 VP + 有对手时的竞争战果 2/3；并列赢家向上取整平分；个人奖励另算 |
| 败北 | 与普通输掉战斗的结果概念明确区分；出牌资格、忽略赢家比较、持续与清理按适用规则处理 |
| 淘汰 | 第 8/9/10 回合分别至少留 4/3/2 名，截线同分保留，不按座位或军绩强制裁员 |
| 最终胜负 | 第 11 回合最高 VP；同分检查本回合深山町胜者；不能唯一决出时圣杯溢出、全员失败 |

### 5.1 地图与视觉验收

遵循原棋盘功能关系及已有 UI 重设计交接：中央地图为主，六名对手紧凑排列，本人操作台位于底部，顶部显示回合、阶段、顺位和当前行动者。参考图用于布局，不作为规则来源。

- A1/A2：区分局势牌库和当前激活局势；牌数由后端返回，不硬编码为 11。
- B1/B2/B3：事件牌库、深山町明置事件、新都暗置/已展示事件；支持同一战场多张事件与牌堆重洗。
- C/D：工房 +2/+1/+1/+1 与两战场 +3/+1 槽位；普通进入者独立显示，不根据当前人数自动递补加成。
- E/F/G/H：移动成本放在连接线上；竞争战果、侦查 2 VP 和排行榜清晰可见。
- 工房通常容量 4，第 10/11 回合通常 1；真实容量和例外必须来自后端。
- 主界面始终能回答“谁在行动、现在要做什么、我的合法选项有哪些、为什么不能操作”。
- 1440×900、1920×1080 不出现页面横向滚动；长牌区可独立横向滚动。检视不被容器裁剪，关闭最上层后保留原公开信息面板。
- 支持键盘焦点、Esc、减弱动效；不依赖颜色或音效作为唯一状态提示。

## 6. 单一前后端契约

继续以主仓库 `src/application/integration-contract.ts` 为面向 UI 的契约入口。本地 `PlayerMatchView`、`AbilityPlayerView`、`PlaytestClientFixture` 是迁移来源，不应成为三套永久并行 API。

```text
原始牌图/HTM + 人工确认
  → authoring JSON → 编译校验/能力报告
  → 主仓库内容适配 → SkillRegistry/规则解释执行
  → GameApplication：唯一权威命令入口
  → 玩家安全 MatchView + AvailableAction + 事件/计算/拒绝
  → 中文桌面 UI
```

P0 建议使用本机服务承载权威应用和存档，以本机浏览器渲染 UI；资源随版本打包。后续局域网复用同一应用入口。原生桌面壳可后置，不把规则直接编进 UI 来绕过服务接入。

| 契约 | 内容要求 | 接入必须补齐的边界 |
|---|---|---|
| MatchView | 当前玩家可见状态、阶段/步骤、私有区与公开区 | 显式字段白名单，禁止通过 Omit + 展开剩余状态夹带内部字段 |
| AvailableAction | 可执行意图、候选、数量限制、来源关联、后端计算信息 | 覆盖开局、部署、移动、成组出牌、能力、决策、合法结束，不只返回技能与结束 |
| GameCommand | 实例及选择、commandId、gameInstanceId、actorId、expectedRevision | actorId 由会话绑定校验；UI 不提交最终费用、威力、胜者或无授权忽略限制开关 |
| CommandResult | revision、新投影、下一组动作、可公开事实与计算；或结构化拒绝 | 拒绝原子回滚；事件与计算也按接收者过滤，不能只过滤 view |
| CardDefinition | canonical ID、中文原文、图片、牌面、完整规则扩展 | 静态图鉴与当前隐藏实例的对应关系分开，不能借 ID/日志推断隐藏身份 |
| HostAdjudicationRequest | 来源、原因、版本、上下文、允许操作 | 只在开发房出现，并连接真实主持人授权及后端处理器 |

字段完整性要求（建议补齐语义，正式字段名在主线契约修订时统一）：

- 地点：canonical locationId、实际容量、进入方式、累计部署序号、槽位 ID、当前有效加成。
- 卡牌实例：instanceId、可见时的 definitionId、owner/controller、区域、明暗、激活、可见使用次数、来源关系。
- 决策：decision/window ID、可见候选、min/max、当前资格、可否取消/放弃、版本；续执行数据留在后端。
- 状态：有效期、来源、堆叠与到期原因；公开部分用于 UI，隐藏部分仍留在权威状态。
- 持久化：规则版本、内容版本/哈希、初始种子与 RNG 状态、revision、命令去重记录、未完成决策和续执行位置；仅权威存档持有秘密。

本地地点 ID `magic_workshop/miyama_town/shinto/recon` 分别适配主仓库 `workshop/mountain/city/scouting`。旧角色 ID 进入 aliases，不通过中文显示名推断身份；例如 `servant.francis_drake → servant.drake`、`servant.suzuka_gozen → servant.suzuka`。

## 7. 卡牌能力实现策略

沿用已确认的 `cardFace`、`playRequirements`、`playTiming`、`abilities[]` 分层。每个能力保留 `printedClause` 中文原文，使用条件、能力额外费用、targets、responseWindow、effects、lifecycle、ruleModifiers、creates/copies/transforms、受控公式按标准化文档表达。

空功能采用文档约定的省略/编译展开方式，不要求维护者填写所有空对象。未知语义进入报告，不靠 OCR 或字符串执行猜测。真正改变基础规则的能力由对应合法性、费用、结算入口读取修正器。

阿尔托莉雅·卡斯特用于覆盖 X 费用、私有选牌、残留、动态威力、共同胜利、唯一响应和派生牌等交互，但不作为全部卡牌机制已实现的证据。其他首发卡出现的机制也必须逐条验收。

两层能力状态必须分开：

1. **内容确认状态**：文字、属性、归属是否经证据确认。
2. **运行支持状态**：在指定规则版本和执行器中是 FULL、PARTIAL、需主持人还是不支持。

本地 `automatic` 只证明对应本地解释器支持，不能直接宣传为主仓库 FULL。主仓库 FULL 至少要求：依赖齐全、handler/解释程序可加载、合法动作可发现、真实命令成功执行、投影正确、存档可恢复，并有实际样例测试。

适配输出保留完整 `rules` 语义并报告未映射项。主仓库当前已引用 `ruleProgram`，但程序文件缺失；需要先恢复其实际实现再确定与 authoring 的映射，不能根据缺失接口建立第二套不兼容执行器。
